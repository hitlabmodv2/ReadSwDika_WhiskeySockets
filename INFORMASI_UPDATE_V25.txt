> Berguna saat view once di GC tapi tidak mau media muncul ulang di GC — cukup ketik `.rvo2`, media langsung masuk DM bot

3. Hasil tampil realtime di body pesan: bar visual `█░░░░░░░`, persentase, used/total/sisa, ikon 🟢🟡🔴 sesuai level
4. Saat `ramAutoDetect ON` — limit dihitung langsung `total RAM × persentase`, bukan angka tetap
5. Section baru *🤖 ᴀᴜᴛᴏ-ᴅᴇᴛᴇᴋꜱɪ & ꜱɪᴍᴘᴀɴ* ditambah di button single-select — posisi *paling atas* agar langsung terlihat:
   • _⚡ Save Semua Sekaligus_ — simpan RAM limit + disk limit + warn otomatis ke `config.json` dalam sekali klik
   • _🧠 Save RAM Limit_ — simpan `total RAM × persentase` ke config
   • _💾 Save Disk Limit_ — simpan total disk terdeteksi ke config

*13. ⏰ Jadibot V1 & V2 — Notif Pairing Timeout (3 Menit) Tidak Pernah Terkirim — Bug*
~Bug: saat orang diam 3 menit tidak masukkan kode pairing, bot tidak merespons sama sekali — tidak ada notif ke nomor target maupun ke owner/GC~
1. _Penyebab utama:_ timer 3 menit diset di event `connection 'connecting'`, tapi saat koneksi pairing putus otomatis setelah 3 menit, event `connection 'close'` lebih dulu jalan dan langsung panggil `clearTimeout` — timer terbunuh sebelum sempat jalan
2. _Efek lanjutan:_ setelah timer dibunuh, handler `isJadibotExpired` di bawahnya tetap jalan dan panggil `expireJadibot` — akibatnya nomor target malah menerima pesan *"jadibot expired"* yang salah konteks _(beda isi, beda tombol)_, bukan pesan *"kode pairing habis waktu"*
3. _Fix:_ di event `connection 'close'`, deteksi dulu apakah sesi ini masih di tahap pairing _(belum pernah konek, belum registered, belum di jadibotMap)_ — kalau iya, kirim notif pairing-timeout langsung di sini sebelum `clearTimeout`, lalu `return` agar `expireJadibot` tidak ikut jalan
4. Notif dikirim ke *dua pihak* sekaligus, tidak saling bentrok:
   • *Nomor target* → pesan "Kode pairing habis waktu, hubungi owner" + tombol URL langsung chat owner
   • *GC/owner* → pesan "Pairing gagal" + command `.jadibot xxx` untuk coba ulang
5. Guard idempotensi (`pairingTimeoutNotified` Set) ditambah — kalau ada race condition antara timer dan close event, notif tetap hanya dikirim *satu kali*, tidak dobel
6. Guard null `sendReply` ditambah — tidak crash jika sendReply tidak tersedia
> Sekarang saat orang diam 3 menit tidak masukkan kode, kedua pihak langsung dapat notif yang tepat dan berbeda — tidak ada lagi yang bingung atau tidak tahu apa yang terjadi

*17. ⚙️ SW Tracking — 3 Optimisasi Internal (Atomic Write, TTL Cleanup, REVOKE LRU)*
_Tiga perbaikan internal di sistem SwTrack agar lebih stabil & efisien di produksi jangka panjang:_
1. *Atomic Write* — semua penulisan JSON (swstats, swtrack user, config jadibot, dan REVOKE) kini tulis ke `.tmp` dulu lalu rename — kalau proses crash di tengah, file asli tidak pernah korup
2. *swProcessingSet TTL Cleanup* — Set dedup story sebelumnya hanya di-add, tidak pernah dibersihkan → lama-lama tumbuh tak terbatas; sekarang ada cleanup otomatis tiap 30 menit, entry >2 jam dihapus — memory tetap terkendali walau bot jalan berhari-hari tanpa restart
3. *REVOKE LRU Fast Path* — saat story dihapus pengirim, sistem tidak lagi scan semua file user satu-satu (O(n)); sekarang ada LRU map `msgId → nomor HP` di memori (max 5000 entry, FIFO eviction), lookup O(1) langsung ke file pemilik — kalau LRU miss tetap fallback ke full scan otomatis, tidak ada regresi
> Tidak ada perubahan di tampilan/perintah pengguna — semua transparan di dalam sistem
